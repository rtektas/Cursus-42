# webserv

## Description

**webserv** is a fully custom HTTP/1.1 server implemented from scratch in C++98, inspired by the architecture and configuration style of NGINX. The goal of the project is to understand how a production-grade web server works internally by building one that can handle real HTTP traffic: parsing requests, routing them according to a configuration file, serving static files, handling file uploads and deletions, running CGI scripts, managing cookies, and returning correctly formatted responses — all without relying on any external HTTP or networking libraries.

The server is single-threaded and event-driven, relying on `poll()` for I/O multiplexing so that it can handle many simultaneous non-blocking connections efficiently.

## Architecture

![webserv architecture diagram](./webserv-diagram.png)

The codebase is organized into seven modules:

**- a_config_parser** — `ConfParser` reads and tokenizes the configuration file; `ServersConf`, `ServerConf`, `LocationConf`, and `RouteConf` build the resulting server/location/route objects; `Validation` checks the parsed configuration for correctness before the server starts.

**- b_request** — `HTTParser` drives request parsing, split across `process_req_line`, `process_headers`, and `process_body` for the request line, headers, and body (length- or chunk-based) respectively; `Request` and its parsing structs hold the parsed result.

**- c_response** — `ResponseBuilder` dispatches to the correct builder depending on the request type: `build_static`, `build_upload`, `build_delete`, `build_autoindex`, `build_cgi`, and `build_error`; `PageError` maps status codes to error pages.

**- d_client** / **e_server** — `Server` owns the listening sockets and runs the main `poll()` event loop, accepting new connections and dispatching ready file descriptors; `ConnectionManager` owns the pool of active `Client` objects (bounded by a max active client count) and handles adding/removing clients; each `Client` tracks its own read/write buffers, timeout, and CGI/keep-alive state.

**- f_cgi** — `CGIHandler` forks and manages CGI child processes, builds the CGI environment (`cgi_env`), pipes request bodies to the script's stdin and reads its stdout (`on_stdin_ready` / `on_stdut_ready`) without blocking the event loop, and resolves the interpreter to use (`parse_interpreter`) based on the configured extension mapping.

**- g_utils** — shared utilities: logging (`Logs`), file reading (`ReadFile`), signal handling for graceful shutdown (`Signals`), type conversions (`Convertion`), autoindex HTML generation (`HtmlGenerator`), and other generic helpers (`Object`, `Search`, `Options`).

## Features

**Request/Response handling** **-** Custom HTTP/1.1 parser handling the request line, headers, and body

**-** Request bodies supported via both `Content-Length` and chunked transfer encoding

**-** Response builder covering static file serving, uploads, deletions, autoindex, CGI output, and error pages

**-** Support for `GET`, `POST`, and `DELETE` methods, enforced per-location by the configuration file

**Networking** **-** Single-threaded, non-blocking, event-driven architecture built entirely on `poll()`

**-** One listening socket per configured `host:port`, each set to `SO_REUSEADDR` and non-blocking, all monitored in a single `poll()` loop alongside client sockets and CGI pipe file descriptors

**-** New connections get `TCP_NODELAY` and are handed to a connection pool with a configurable max active client limit; if the pool is full, new connections are rejected and logged

**-** Idle client connections are dropped after a configurable timeout (returning `408 Request Timeout` if a request was mid-flight); CGI processes are watched for their own timeout independently

**-** Keep-alive is handled per request based on the `Connection` header, resetting client state for reuse when applicable

**CGI** **-** Unlimited number of interpreters, mapped per file extension via `cgi_handler` directives in the config (e.g. `.py`, `.php`, `.pl`, `.sh`, or arbitrary custom extensions)

**-** CGI processes are run non-blocking: `stdin`/`stdout` pipes are added to the `poll()` set, so a slow or hanging CGI script cannot stall the rest of the server

**-** CGI-generated headers (including `Set-Cookie`) are parsed and merged into the final HTTP response

**Cookies** **-** Cookies can be parsed from incoming requests, set by the server, or generated by a CGI script

**-** Cookie data can be persisted both server-side and written back to the client

**Configuration** **-** NGINX-style config file supporting multiple `server` blocks (virtual hosts distinguished by port and/or `server_name`)

**-** Per-location settings: allowed methods, document root, index file, upload directory, redirects (e.g. `return 301 ...`), and body size limits

**-** Custom error pages configurable per status code; the project handles 400, 401, 403, 404, 405, 408, 409, 411, 413, 414, 415, 431, 500, 501, 503, and 504/505 responses

**Other** **-** Directory listing (autoindex) with generated HTML

**-** File upload (to a configurable `upload_store` directory) and file deletion via `DELETE`

**-** Request/connection/error logging

**-** Graceful shutdown on `SIGINT`/`SIGTERM`, closing all client connections before exit

## Instructions

### Requirements

**-** Linux

**-** A C++98-compatible compiler (project is compiled with `-Wall -Wextra -Werror`)

**-** `make`

### Compilation

```bash
make
```

This builds the `webserv` executable using the provided Makefile (`make`, `clean`, `fclean`, `re` are all available).

### Execution

```bash
./webserv [configuration_file]
```

If no configuration file is provided, the server falls back to a default configuration.

### Configuration file

The configuration file uses an NGINX-inspired syntax. It is organized into one or more `server` blocks, each defining a listening port and, optionally, a server name. Each `server` block contains one or more `location` blocks that define how requests to specific paths are handled — including which HTTP methods are allowed, the document root, index files, upload directories, redirects, body size limits, and CGI interpreters mapped by file extension. Custom error pages can also be defined per server.

Several example configuration files are provided in the repository, ranging from a minimal single-server setup to a multi-site configuration with CGI, uploads, cookies, and custom error pages.

## Usage Examples

With the server running (`./webserv webserv.conf`) on port 8080:

```bash
# Basic GET request
curl http://localhost:8080/

# POST a file upload
curl -X POST -F "file=@image.png" http://localhost:8080/upload

# DELETE an uploaded file
curl -X DELETE http://localhost:8080/upload/image.png

# Hit a CGI endpoint (Python)
curl http://localhost:8080/cgi-bin/script.py

# Trigger directory listing (autoindex) on a directory with no index file
curl http://localhost:8080/directory/

# Trigger a client error (body too large)
curl -X POST --data-binary @big_file http://localhost:8080/post_body
```

## Technical Choices

**- `poll()` over `select()`/`epoll()`**: `select()` is limited by `FD_SETSIZE` and has O(n) scanning overhead similar to `poll()` without the flexibility; `epoll()` is Linux-specific and edge-triggered semantics add complexity. `poll()` was chosen as a straightforward, portable middle ground well suited to the project's connection volume, while keeping the whole event loop centered on a single `poll()` call as required by the subject.

**- Single-threaded design**: avoids the synchronization complexity of a multi-threaded server; concurrency is achieved instead through non-blocking I/O and the `poll()` event loop, including for CGI pipes.

**- C++98**: mandated by the subject; standard library containers (`std::map`, `std::vector`) are used throughout in place of hand-rolled data structures.

**- NGINX-inspired configuration syntax**: chosen so the config format is familiar and easy to reason about, while only implementing the subset of directives relevant to the project's scope.
